# CLI Reference

The `rlmesh` binary hosts real-time sessions on a machine (`rlmesh host`) and manages the devices that join them, watches a session in the cockpit, checks and probes env and model images, and signs in to a managed RLMesh platform to submit and watch evaluations. It ships inside the Python package as `python -m rlmesh` and the `rlmesh`, `rlmeshd` (`rlmesh host`) and `docker-credential-rlmesh` console scripts, and standalone (`cargo install rlmesh-cli`, which leaves the cockpit out unless built with `--features cockpit`).

`rlmesh --help` and `rlmesh <command> --help` are the authoritative flag lists. This page describes the behavior around them.

## Pre-push checks

`rlmesh check` and `rlmesh check-image` sort what they find into three buckets and exit 1 only on the first: **failed** (the push would land as not-runnable, or the platform would reject a claim), **warnings** (a claim the platform trims, or intent it cannot see), and **not checked** (what could not be decided on this machine, and who decides it instead). `--json` prints `{"failed", "warnings", "not_checked", "passed"}`, each a list of strings.

`rlmesh check MODULE:CLASS` runs the Python describe on the class, in the interpreter `RLMESH_PYTHON` names (the `python -m rlmesh` entrypoint sets it to its own; else the first of `python3` / `python` that imports `rlmesh`). It fails on a model without a `spec` (`rlmesh doctor` needs a `ModelSpec` to synthesize inputs without a reference env), a spec or tags that does not resolve, tags that do not fit the env's spaces (joined per contract branch, as `rlmesh.serve` does at startup), a contract branch without tags, a broken `model_spec` / `env_tags`, a workflow edition declaration this build cannot run, or a class that does not import. It warns on an env without `tags` (it runs against spec-less models, but the platform cannot adapt a spec'd model to it), on ad hoc roles a curated publish gate would refuse and on best-effort badges elsewhere in the envelope. Building the env for its spaces is best-effort: when it needed a GPU, a display, or assets this machine lacks, that is reported as not checked, not failed.

`rlmesh check-image IMAGE` reads `docker image inspect` and checks: the command runs `python -m rlmesh.serve` with a `module:Class`, `--env` if and only if the describe label says the image is an env, no baked `--address` (warning: it would override the address supplied at container startup), no image-level `ENV RLMESH_ADDRESS` (warning), `EXPOSE` of the four ports its session listens on (warning: the base port, 7447 unless the image's `RLMESH_ADDRESS` or baked `--address` names another, and the next three, one per traffic class; participants dial `HOST:7447#KEY/NAME`), `linux/amd64`, the `dev.rlmesh.describe` and `dev.rlmesh.package` labels when present (a missing describe label is a note: the platform reads describe off the handshake), and, when the describe label advertises editions, whether the image's rlmesh shares a workflow edition with the platform, negotiated the way the runtime does at bind time. The platform's editions come from `--platform-editions 2026.10,...` (the list `rlmesh version` prints as `Editions` on the platform's rlmesh), from `--platform-version VERSION`, or default to this CLI's own rlmesh. Two assumptions behind `--platform-version`: only this CLI's own version is known, since each release retains its own edition list, so any other version leaves the edition check as not checked and asks for `--platform-editions`; and version spellings are normalized, so `0.2.0a0` (PyPI) and `0.2.0-alpha.0` (Cargo) name the same build. A custom entrypoint (not `rlmesh.serve`) is not checked by `check-image`; use `rlmesh doctor` to test it at runtime. A native (C/C++) env publishes describe on its handshake through the C ABI when it binds; bake its `rlmesh_ext_env_server_describe_json` output as the `dev.rlmesh.describe` label to describe the image before it runs. The image's compute variant is validated, reported under `variant:`, `profiles:`, and `rows:`. Failures cover: keys, facets, `requires` constraints and vendor rules (`accel.vram` is a quantity string such as `"24Gi"`), priority, `gpu.count`, at most one default profile, and derived row keys. Warnings cover contradictions with the image metadata (for `accel.cuda`, including upper bounds): a declaration the image's `CUDA_VERSION`, `NVIDIA_REQUIRE_CUDA`, `ROCM_VERSION`, or describe `framework_versions` contradict. An image without a variant block gets a line reporting the requires the platform infers for it, and the row keys it would get (see [Publishing compute variants](../compute-variants.md#what-check-image-validates)).

## Publishing compute variants

`rlmesh registry publish ns/pi0:v3`, with no images named, reads `rlmesh.toml` in the current directory (`--config FILE` names another, `-` for stdin): the version's `dev.rlmesh.package` label written in TOML, with one `[variant.KEY]` table per build in priority order, its requirements as `accel.*` keys. Every problem in the file is reported at once against its place in it, checked by the same rules as `check-image`. A version tag already in use is refused before anything is built, unless `--force`. Each variant is then built with `docker buildx build --platform linux/amd64` from its `dockerfile`, `target` and `build_args`, its label rendered in, pushed as `TARGET-TAG-KEY` with OCI media types, and the builds are published as below with the file's version-level keys as the index annotation. `--dry-run` builds nothing and prints each build, its requirements and row keys, and the build commands; `--dry-run --json` prints each build with its rendered label, and the index annotation.

`rlmesh registry publish ns/pi0:v3 ns/pi0:v3-cuda12 ns/pi0:v3-rocm6 ns/pi0:v3-jax` publishes a version: an OCI image index whose children are the given images, one compute variant each. Each source must already be pushed and must be one linux image; a BuildKit image index with attestations counts, and its attestations are carried along. Sources are pinned by digest before the index is created. Every carried attestation must describe an image of the version, and an index source's declared platform must match its image config. Every child must carry a `dev.rlmesh.package` label with a `variant` block (a lone child may leave it out, and is keyed `default`) that passes the `check-image` checks. Variant keys and the row keys the platform derives (`<variant.key>-<profile.key>`) must be unique, all children must serve the same kind, and at least one child must be `linux/amd64`; any other platform is a warning, since the platform records that child as `excluded`. The index annotation may carry only the version-level keys (`name`, `description`, `checkpoints`, `compatibility`, `capabilities`, `inputArtifacts`); others are warned about. Every check that can run before pushing runs first, and every problem across all sources is reported at once, before anything is pushed. `--tag` adds tags in TARGET's repository, `--channel latest` adds a moving channel tag, and `--index-package FILE` sets version-level JSON (checkpoints, compatibility) as the index's `dev.rlmesh.package` annotation. `--index-package` needs an OCI image index, so it is refused when every manifest the sources carry (images and attestations) is a Docker schema2 manifest (docker would assemble a Docker manifest list and drop the annotation), and the index docker assembles is checked to carry it before the push and as stored after it. A single index source published without `--index-package` keeps its own index annotation, which is checked by the same rules. TARGET and each `--tag` do not move to a different index without `--force`, and a tag counts as new only when the registry says it does not exist (under any spelling docker resolves to it: `ubuntu:v1` is `docker.io/library/ubuntu:v1`): one that cannot be read (authorization, transport, a registry error, output that does not parse) is refused without `--force`, with the reason. A tag already holding the same index (compared as stored: media type, manifests in order, annotations, `subject`, `artifactType`) is not pushed again, so publishing again never moves TARGET; another tag holding it at another digest (another serialization) is re-pointed at TARGET's. The index is pushed to TARGET alone and checked as the registry stores it (the index assembled and, with `--index-package`, an OCI image index carrying the annotation); only then are the `--tag` and channel tags pointed at TARGET's digest, which is also what they point at when TARGET already holds the index, so every tag is the same manifest. If that check fails, only TARGET has moved, and the error says what it pointed at before and how to recover: put the previous digest back with `docker buildx imagetools create --tag TARGET REPOSITORY@DIGEST`, or publish again with `--force` once the cause is fixed. The channel tag moves, printing the digest it moved from or why it could not be read, unless it is also TARGET or a `--tag`, which keeps it protected. `--dry-run` prints the per-variant table, the index JSON, and each tag's state without pushing, and fails on a tag the real run would refuse. The registry is reached through `docker buildx imagetools`, so docker's credential helpers apply; run `rlmesh registry login` first for the platform's registry. The label schema, the buildx workflow, and what the platform does with variants are in [Publishing compute variants](../compute-variants.md).

`rlmesh describe MODULE:CLASS --label` is for an image with a custom entrypoint (one that does not run `python -m rlmesh.serve`, so the platform cannot read describe off the handshake). The envelope records the machine it ran on: its OS and architecture, package versions, editions, and whatever env the machine could build. The platform fails a label whose `runtime.os` is not `linux`, and `check-image` fails it the same way, so generate the label inside the built image and add it in a second, cached build:

```bash
docker build -t my-model:latest .
docker build --label "$(docker run --rm --entrypoint rlmesh my-model:latest describe my_pkg:Policy --label)" -t my-model:latest .
```

The describe envelope's `runtime` block carries what the served peer's handshake will send, under the handshake's names: `protocol_generation`, `supported_workflow_editions` (every edition its rlmesh can drive, newest first) and `preferred_workflow_edition` (what the server resolved: `--workflow-edition`, `RLMESH_WORKFLOW_EDITION`, the class declaration, or `[tool.rlmesh]`, else that build's newest); `runtime.workflow_edition_error` is present when the declaration names an edition that rlmesh cannot run, and both `check` and `check-image` fail on it since `rlmesh.serve` would refuse to start. See `docs/specs/describe.v1.md`. `python -m rlmesh._describe` is the module behind both commands: `TARGET [--label]`, `--check-entrypoint MODULE:CLASS`, `--check IMAGE`, `--check-labels FILE`, each with `--json`.

## Files

- `config.toml` (config directory): the default profile and, per profile, the platform URL, the token endpoint the profile signed in against, the registry host handed to docker, and the identity the platform last confirmed. Never holds a credential.
- `credentials.json` (data directory, mode 0600): the access and refresh token per profile, used only when the OS keychain is unavailable or `RLMESH_KEYCHAIN=off`. Otherwise credentials live in the keychain under the service `rlmesh` with the profile name as the account.
- `<profile>.lock` (data directory): held for the duration of a session refresh so concurrent commands rotate the session once. A lock older than 30 seconds is treated as abandoned.
- `~/.docker/config.json` (or `$DOCKER_CONFIG/config.json`): `rlmesh registry login` adds a `credHelpers` entry mapping the registry host to `rlmesh`.
- `host.key`, `local.key` (rlmeshd's state directory, mode 0600): the host's static X25519 key and Ed25519 seed, and the key of its device `local` (`{local secret}.{host key}`, as an address carries it). Made on first start and kept, so the host's identity survives restarts.
- `devices.toml` (rlmeshd's state directory): `[devices.ID]` entries (`public_key`, `max_priority`, `parts`, `verbs`, and `kind` and `name` from pairing) and `[robots.NAME]` pins (`device`, `board_id`). `rlmesh devices` rewrites it whole, comments dropped.
- `pair.sock` (rlmeshd's state directory, mode 0600): rlmeshd's local channel, which `pair approve` and `devices provision` reach it by.
- `~/.config/rlmesh/hosts/{host id}.toml` (or under `$XDG_CONFIG_HOME`, mode 0600): a paired machine's record of one host: its `host_id`, `host_key` and `addresses`, and this machine's `device` id and `device_key` there.
- `~/.config/rlmesh/browsers.toml` (or under `$XDG_CONFIG_HOME`, mode 0600): the browser tokens paired on this machine, `[browsers.DEVICE]` with the host's `host_id` and `host_key`, the token's hash (`token`, never the token) and the device's `device_key`; `rlmesh-gateway` reads it (`--browsers`).

## Session lifecycle

The access token is a short-lived JWT. A command reuses it while it is more than a minute from its `exp` claim, so `rlmesh token`, `rlmesh eval ...`, and every docker pull cost no round trip to the identity provider. Only an expired token triggers the `refresh_token` grant, under the profile lock, and after re-reading the credential store in case another process already rotated it. A request the platform still rejects as unauthorized is retried once after a forced refresh. Refresh tokens are single use, so a session that two machines share stops working on one of them after the other refreshes; sign in on each machine instead.

`rlmesh org switch` re-issues the session with the identity provider's `organization_id` extension to the refresh grant, then confirms the active organization from the new token and from the platform.

`rlmesh logout` calls the platform's session-revocation route before deleting the local credential. A platform without that route, or one that cannot be reached, is reported in one muted line and the local sign-out proceeds.

## Doctor and bench

`rlmesh doctor IMAGE` runs the image in a container (the way `SandboxEnv` and `SandboxModel` run a prebuilt image, removed afterwards), waits for it to serve, and checks its handshake, describe envelope and conformance. It writes `probe-report.json`. `image_config` comes first: `check-image`'s checks of the image config and labels, so an invalid describe label fails there.

What the image is probed as comes from its describe label's `kind`, else from `--env` on its `rlmesh.serve` command; `--kind` overrides both.

- An **env** is bound with the random baseline and stepped with the probe's own actions: `env_handshake`; `env_spec_matches_describe` (the live spaces and tags against the label, skipped without one); `env_contract` (the branch it serves against the label's branch table); `env_repro` (a seeded reset and ten seeded steps replayed twice, state exactly and images within renderer jitter); `env_step_conforms` (one neutral step whose observation must fit the space); `env_step_latency` (p50 and p95 of 20 steps); and `preview`, 60 frames of the main camera (`image/primary`, else the first image leaf) written as `probe-preview.mp4` (AV1) and `probe-preview.png`.
- A **model** is bound to a stand-in env built from its `ModelSpec` (one observation leaf per input role, an action the width of its output), served in the model's own session, so resolution is the binder's own: `handshake`, `resolve`, `shape_single`, `shape_batch` (two sessions at once, which the model's batcher may fuse), `determinism_floor` (unseeded episodes on one input), `seeded_repro` (episodes seeded alike, then two seeds apart for a sampling model) and `stateless` (input A, B, A in one episode). A model that declares no `ModelSpec` needs `--env IMAGE`: the stand-in then takes that env's spaces and tags, and the env is never stepped. Without one the handshake warns and the rest is skipped.

`rlmesh bench IMAGE` runs the same handshake, then drives 1, 2, 4, ... 32 stand-in sessions at once (`--sizes`) for 3 untimed and 20 timed predicts each (`--iterations`). Each point reports the p50 and p95 predict time and predicts per second; the recommended `max_batch_size` is the size with the best throughput whose p50 stays within 250 ms (or twice the single-session p50), where a larger size takes over only by gaining 10%. A size slower than the one before is measured twice. Set the served model's batcher with `rlmesh.BatchOptions(max_batch_size=...)`, or, for an image that runs `python -m rlmesh.serve`, with `RLMESH_MAX_BATCH_SIZE` in its environment (`--max-batch-size`; every `BatchOptions` field has a flag and a variable, which `python -m rlmesh.serve --help` lists).

Both join the container's session as clients of its host, as the container's own participants do.

## Eval reports

`rlmesh eval report` and `rlmesh.EvalReport` (Experimental) read result bundles as `RunResult.load` does: a bundle of one or several workloads, or a folder of bundles in name order. A workload's task is its `task`; its suite is the `suite` key of its `config` (`Recorder.add(..., task="pick-0", config={"suite": "libero_spatial"})`). The report computes:

- Success counts the episodes recorded with `included_in_metrics`; one with no success signal counts as a failure and is reported as `unknown`. The interval is the Wilson score interval at 95%.
- Steps and wall time are each episode's env steps and reset-to-end seconds, totalled and averaged.
- Telemetry rows of one series (`op`, `component`, `metric`) merge as follows: counts add, and `avg` and each percentile are count-weighted means. A bundle keeps each run's whole-run rows (nearest-rank percentiles), so no warm-up is discarded.

## Local runs

`rlmesh eval run` expands the request into workloads and runs them locally: each model in one `SandboxModel` container, one at a time, and each of its workloads as one route of `Model.run_routes` against a `SandboxEnv` container of its own, in waves of at most `--max-envs` (16) live env containers. It needs Docker and a Python with `rlmesh` (`RLMESH_PYTHON`, as for `rlmesh check`).

- **Plan.** Models × tasks; a task's episodes split over `workers` (absent: one worker per episode, scaled back to 300 workers per run), the remainder on the first workers. Every workload's seeds derive from the task's `seed` (0 by default), its seed key (the env and scenario, `<env>:<group>/<scenario>`, or `metadata.environmentId`) and the global slot of each episode, so every model and every split draws the same episodes. The trial ordinal of an episode is its slot. `crates/rlmesh/conformance/eval_plans.v1.json` pins the expected workload plans.
- **Catalog rules.** The env's make kwargs and the episode cap come from the images themselves: the scenario a `taskId` names (`<group>/<scenario>`) from the env's describe envelope, and the model's pairing for the env (with per-scenario refinements, and `max_episode_steps` as the cap) from the model's `dev.rlmesh.package` label. An env that declares `requiresEpisodeCap` does not run under a model that binds no cap. A catalog changes these by rebuilding its images.
- **Names.** Without `--catalog`, `model` and `env` are image references. With it, `prebuilt/<model>/<env>` and `prebuilt/<env>` are the local build `rlmesh-<model>-<env>:TAG` when one exists (`latest`, or the `--catalog=TAG` given), else `registry.rlmesh.dev/prebuilt/...`, pulled on first use.
- **Refused fields.** Fields only the platform can honour are refused by name before anything starts: `projectId`, `managed`, `resources`, `residentKeepAliveSeconds`, `timeoutSeconds`, `maxAttempts`, `maxBatchSize`, `batchWindowMs`, `maxInFlightBatches`, `clientsPerServer`, `record`, `models[].variant`, `models[].resources`, `tasks[].record`, `tasks[].perturbation`, `tasks[].variant`, `pairing: "transfer"`, a checkpoint URI, and any `envVars` key besides `RLMESH_MAKE_KWARGS`. `maxActionChunk`, `asyncPrefetchLead`, `metadata` and `tags` are honoured or kept in the index.
- **GPUs and mounts.** An image whose package declares `resourceClass: gpu` needs `--gpus` (`docker run --gpus`). `--volume` mounts into every container, such as a checkpoint store at the path the package label's checkpoints name.
- **Output.** `<out>/index.json` holds the request, the plan, each image's id and each workload's status; `<out>/workloads/<id>` is each finished workload's `rlmesh.result.v1` bundle, its task the request's `taskId` and its `config` carrying `suite` (the scenario's group), the seed key, slot offset and shard. `--resume` reruns only the workloads whose bundles do not hold their planned episodes; a workload is the unit it resumes. Each image reference resolves to its image id once, when the run starts, and every container (each wave's model and envs included) runs by that id, so a tag moved mid-run changes nothing. A different request in the same `--out` is refused, and so is a resume whose plan or image ids changed (an image rebuilt or retagged since), so one report never mixes two models' weights. An `index.json` written before runs recorded image ids is refused too, as one whose images cannot be verified: start it again in another `--out`.

## Platform contract

The CLI has no built-in identity provider. Everything it needs comes from the platform it signs in to, so a provider change is a platform deploy rather than a CLI upgrade. A platform that wants to be driven by this CLI serves:

- `GET /v1/info` (unauthenticated): `auth.cli.clientId` (the OAuth public client id the CLI presents), `auth.deviceAuthorizationEndpoint`, and `auth.tokenEndpoint`, plus `urls.dashboard` for the links `eval submit` prints. Other fields, `auth.issuer` included, are ignored. Endpoints must be `https://` (plain `http://` is accepted only for loopback hosts). The document only ever gains fields.
- The device flow of RFC 8628 at the advertised endpoints: `POST deviceAuthorizationEndpoint` with `client_id` returns `device_code`, `user_code`, `verification_uri` (optionally `verification_uri_complete`), `expires_in`, and `interval`; the CLI then polls `POST tokenEndpoint` with `grant_type=urn:ietf:params:oauth:grant-type:device_code` and honors `authorization_pending`, `slow_down`, `access_denied`, and `expired_token`.
- The `refresh_token` grant of RFC 6749 at the token endpoint, with one extension: an `organization_id` form field asks for the session to be re-issued against that organization. Refresh tokens rotate on use. The token response needs only `access_token` and `refresh_token`; anything else is ignored.
- Access tokens as JWTs whose payload carries the standard `exp` claim. The CLI reads it without verifying the signature, only to schedule refreshes; the platform validates every token it receives, and no other claim is read.
- `GET /v1/me` (bearer): `subject.id`, optionally `subject.email` and `subject.displayName`, and `organization.providerId` plus `organization.name`. The provider id is the id the CLI shows and switches on.
- `GET /v1/me/organizations` (bearer): `organizations[]` with `name`, `providerId`, `active`, and optionally `id` and `registryNamespace`.
- `DELETE /v1/me/session` (bearer): ends the session behind the token; `204` on success, idempotent. A `404` or `405` is treated as "not supported".
- `GET /v1/registry/info` (bearer): `host` and `namespaces[]` of the image registry, whose password is the access token.
- API keys as plain bearer credentials on every `/v1` route, for headless use.

The CLI pins the token endpoint's host per profile at sign-in. If `/v1/info` later advertises a token endpoint on another host, refreshes stop with an error until the user signs in again, so a compromised or misconfigured platform cannot redirect a stored refresh token. A profile stored by a CLI from before pinning existed has no pin and is asked to sign in once more rather than adopting whatever the platform advertises.
