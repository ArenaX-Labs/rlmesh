# Edition 2026.06 errata

These post-release clarifications were formerly appended to the sealed spec.
They are retained here as commentary; the [sealed 2026.06 spec](2026.06.md)
remains the bytes released at v0.1.0. This edition belongs to the 0.1 runner
and is not offered by 0.2.

### Reporting success (clarifies Episode Accounting)

An env reports an episode's task outcome in the info of the step that ends it (the episode's `final_info`); infos from earlier steps are never read for it. The runtime looks under three keys in priority order: `is_success`, `success`, then `task_success`. The first key holding a bool, an integer, or a number decides: a bool as-is, an integer or number as success when non-zero. A key holding any other kind (text such as `"False"`, null, bytes, a list, a map) is skipped and the next key is consulted. When no key decides, the outcome is unknown: it is never inferred from `terminated`, and a run's success rate is unknown whenever any of its episodes' is. The Rust driver and the Python `Session` loop apply the same rule.

### Runtime info keys (clarifies Reset and Step)

The Python remote env clients (`RemoteEnv`, `RemoteVectorEnv`) add two reserved keys to the info dict they return, on top of the env's own keys: `episode_ids` (the runtime-minted episode id per lane, a list) on every `reset` and `step`, and `completed_episodes` (how many episodes ended on that step, `0` when none did) on every `step`. These are client conveniences, not wire fields. An env that reports its own value under either name keeps it, shadowing the client's; the client logs a warning the first time that happens.
