# Running, sessions and results

Part of the [language parity spec](../language-parity.md). Status: Draft —
reviewed round 6. Draft: C# column pending review.

Owns `rlmesh.run`, `rlmesh.session`, `Model.run`, `Model.session`,
`RemoteModel.session`, `Session`, `RunContext`, `RunHooks`, `RunResult`,
`EpisodeResult`, `TelemetryRow`, `StepEvent`, `Reader`, `FrameSources`,
`View`, `Recorder` and its records, `RANDOM_SAMPLE`, and the `ModelTarget` /
`EnvTarget` inputs (R-27). Python sources: `py/_models/_eval.py`,
`py/_models/base.py`, `py/_models/_read.py`, `py/_models/_view.py`,
`py/_client/_remote_model.py`, `py/recorder/`. Rules (R-n) and decisions (D-n)
are in [rules](rules.md); this file does not restate them.

Linked, not owned: `trial_index` ([Env](env.md)), `Model` itself
([Model](model.md)), `RemoteModel` / sandbox handles ([Remote](remote.md)),
`ObservationRoles`, `Advisory`, input leaves ([Adapters](adapters.md)),
`EnvContract` ([Env](env.md)), `Value`, `InfoDict`, `Metadata`, editions
([Core](core.md)).

## Shape

Run with hooks, drive a session by hand, record a run.

```python
class Progress(rlmesh.RunHooks):
    def on_episode_end(self, result):
        print(result.index, result.reward)

result = model.run(env, episodes=10, hooks=Progress())
print(result.mean_reward)

with model.session(env, view="http:9000") as s:
    obs, info = s.reset(seed=0)
    while not s.done:
        obs, reward, terminated, truncated, info = s.step(s.predict(obs))
    rec = rlmesh.Recorder()
    s.run(episodes=50, hooks=rec.capture(model="smolvla", env="libero"))
    rec.export("results/run.zip")
```

```rust
struct Progress;

impl RunHooks for Progress {
    fn on_episode_end(&mut self, result: &EpisodeResult) -> rlmesh::Result<()> {
        println!("{} {}", result.index, result.reward);
        Ok(())
    }
}

let mut hooks = Progress;
let result = model.run(
    &mut env,
    RunOptions { episodes: Some(10), hooks: Some(&mut hooks), ..Default::default() },
)?;
println!("{}", result.mean_reward());

let mut s = model.session(
    &mut env,
    SessionOptions { view: Some(View::parse("http:9000")?), ..Default::default() },
)?;
let (mut obs, _info) = s.reset(Some(0), None)?;
while !s.done() {
    let action = s.predict(obs.clone())?;
    (obs, ..) = s.step(action)?;
}
let mut rec = Recorder::new(RecorderOptions::default())?;
let mut capture = rec.capture("smolvla", "libero", RecorderCaptureOptions::default())?;
s.run(SessionRunOptions { episodes: Some(50), hooks: Some(&mut *capture), ..Default::default() })?;
rec.export_("results/run.zip", RecorderExportOptions::default())?;
s.close()?;

// A vector env or a factory names its kind (RUN-3).
model.run(EnvTarget::vector(&mut venv), RunOptions::default())?;
```

## Parity table

Rust options structs follow R-6 and R-8; C structs follow R-19 (`struct_size`
first, `RLMESH_<NAME>_INIT`, `_MIN_SIZE`); `cancel` fields are R-18's fenced
token. C++ wraps C one to one (D-2): results are value structs copied out of
the C handles.

`RANDOM_SAMPLE` is accepted only by `run` and `session`, the two calls whose
Python signature has a `model` parameter (`py/_models/base.py:1679,1779`); the
methods (`Model.run`, `Model.session`, `RemoteModel.session`) have a receiver,
not a model argument, so they cannot receive it natively either. Its repr is
Python's `RANDOM_SAMPLE` (`py/_models/_coerce.py:18-19`, R-10).

C# targets (RUN-31): `ModelTarget` and `EnvTarget` are `readonly struct`s
with internal representation, converting implicitly from the class types
listed. C# forbids a user-defined conversion from an interface (CS0552), so
an authored `IEnv`, `IVectorEnv` or `IEnvFactory` is named with
`EnvTarget.Local`, `EnvTarget.Vector` or `EnvTarget.Factory`, as Rust names
the vector and factory kinds (RUN-3); each entry point also has one overload
taking an `IEnv` directly, so the common single-env call stays
`model.Run(env)` (an engine component implementing `IEnv` passes `this`).
`RandomSample` reaches only `Api.Run`, `new Session` and `Api.SessionAsync`,
whose model parameter is a `ModelTarget`. A `string` target is copied when
the call starts.

### `RunOptions` (`rlmesh.run`, `Model.run`)

Fields follow `rlmesh.run`'s keyword order, except that `episodes` precedes
`seeds` (RUN-2).

`execution_horizon` is `u32` because Python bounds it to 1..=1024
(`py/_models/_eval.py:775-781`). `prefetch_lead` is a `u64` count (R-5) and
fails with ValueError above `u32::MAX`, the runtime's bound
(`crates/rlmesh-runtime/src/driver.rs:288`; RUN-P1). `max_episode_steps` is a
`u64` count (R-5) and fails with ValueError above `i64::MAX`, the runtime's
`Option<i64>` bound (`crates/rlmesh-runtime/src/spec.rs:192`; RUN-5, RUN-P1),
on both loops. `Model.run` has no `view` keyword in Python;
the shared struct carries it and a local `Model` refuses a set `view` with
TypeError, as `rlmesh.run` does (`py/_models/base.py:1780-1784`; RUN-4).
`True` is `Some(View::default())`; `False` and `None` are `None` (C NULL,
C++ `std::nullopt`; `py/_models/_view.py:164-165`); a string is `View::parse`
(C `rlmesh_view_parse`, C++ `View::parse`). So `rlmesh.run(local_model, env,
view=False)` is accepted, as None is, in every language (RUN-P9).

`max_episode_seconds` crosses C as a `double` (C++ passes its
`duration<double>`'s count). NaN and `<= 0` fail with ValueError (RUN-5,
RUN-P2). `+inf` means no cap and maps to Rust `None`, so a `NEXT_STEP` env
accepts it as it accepts None, in Python too (RUN-P13). A finite value too large
for `Duration` (`Duration::try_from_secs_f64` fails) saturates to
`Duration::MAX`, so it also never fires, as Python's comparison never does. The
same saturation applies to a finite `View` hold in seconds (C `hold_seconds`
with `hold == RLMESH_VIEW_HOLD_SECONDS`, C++ `hold`'s duration alternative; C# `ViewHold.For(TimeSpan)`, where a
`TimeSpan` cannot be infinite or NaN and `TimeSpan.MaxValue` never fires),
whose `+inf`, NaN and negative values fail with ValueError at `validate()` and
at the consuming call, because Python requires a finite hold `>= 0`
(`py/_models/_view.py:147-153`). Rust `ViewHold::For(Duration)` cannot be
negative.

`cancel` (R-18) on `SessionOptions` belongs to the session: C
`RLMeshSessionOptions.cancel` is retained (a new token reference, released at
`rlmesh_session_free`) at creation, and Rust / C++ keep their shared copy.
`cancel_handle()` returns that token, or, when none was given, a token the
session made at creation; it is the same token on every call, and it applies
to every session call (`reset`, `predict`, `step`, `run`, `close`, and the
members that connect). A `cancel` on `SessionRunOptions` or `RunOptions` is
borrowed for that call and applies to it as well: a `cancel()` on either
token fails the call. A `run` / `rlmesh.run` that builds its own session has
only its `RunOptions.cancel`.

C# twins bridge their `CancellationToken` as R-18 states: `RunAsync`
(`Api`, `Model`, `Session`) passes a fresh per-call `Ext.CancelToken` in the
`Cancel` field of a copy of its options, so the token is exact; the
session's single-call twins (`ResetAsync`, `PredictAsync`, `StepAsync`, …)
cancel through `CancelHandle()` and keep R-18's documented completion race.

Hook slots are optional (NULL is Python's no-op default), unlike
`RLMeshRunContextVtable`'s. The `rlmesh_run_hooks_on_*` calls run the slot (or
the library hooks, for a `rlmesh_recorder_capture` handle) and return its
status; a NULL `context`, `event` or `result` fails with
`RLMESH_ERR_INVALID_ARGUMENT`, since the Rust parameters are not optional.
Every pointer a slot receives is borrowed for that call: the
`const RLMeshEpisodeResult*` (copy the struct to keep it), and the
`const RLMeshRunResult*` of `on_run_end`, which a hook keeps, as Python's
hook may keep its `RunResult`, with `rlmesh_run_result_clone` (a new shared
reference to the immutable value, released by `rlmesh_run_result_free`).

Hook errors follow R-12: Rust returns the author's `Error`; C fails with the
class the hook set, `RLMeshException` from `rlmesh_callback_set_error` (a run
hook is an "other" callback kind) or any R-21 class from
`rlmesh_callback_set_error_class`; C++ rethrows the captured exception; C#
rethrows the author's own exception object with its stack (R-12, X-11), and
a .NET exception outside R-21's tree thrown by a hook fails the run as
`RLMeshException` when it crosses C (in process the caller still gets the
original object).

C# hooks (RUN-36): `IRunHooks` declares all five hooks; `RunHooks` is the
abstract base with virtual no-ops, the counterpart of Python's base class,
and also implements `IDisposable` with a virtual no-op `Dispose()`, so the
library subclass `Recorder.Capture` returns frees its C hooks handle with
`using`. An engine component that cannot derive from `RunHooks` implements
`IRunHooks`. The wrapper fills every slot; an empty C# body is Python's
no-op. Lent `RLMeshEpisodeResult` / `RLMeshStepEvent` structs are read by
R-19's whole-field rule and copied into the C# records before the hook
runs, so a hook may keep them; the values inside a `StepEvent` are new
shared references.

C# `ReadFn` and `RenderFn` (RUN-35) are sealed classes, not delegates:

```cpp
class ReadFn {
 public:
  ReadFn() noexcept = default;                 // empty: calling throws rlmesh::ValueError (C's NULL context)
  template <class F>
    requires std::is_invocable_r_v<Value, F&, const ReadItem&>

  Value operator()(const ReadItem& item) const;

 private:
  std::shared_ptr<const std::function<Value(const ReadItem&)>> fn_;
};
```

`RenderFn<'a>` is a struct with private fields, a
`Box<dyn FnMut() -> Result<Value> + 'a>` and a `u64` id drawn from a
process-wide atomic counter at construction: `RenderFn::new(f: impl FnMut() ->
Result<Value> + 'a) -> RenderFn<'a>`, `call(&mut self) -> Result<Value>`, and
`Debug` printing `<function>`. Equality uses the id, not the box address,
because `Box::new` of a capture-less (zero-sized) closure does not allocate
and every such box shares one dangling address; so two distinct closures
never compare equal, and a `RenderFn` equals only itself, as Python compares
the callable by identity. A session's sources borrow the session, a context's
borrow the context. C++ `RenderFn` is
a shared callable class like `ReadFn` (copies keep identity): `RenderFn()
noexcept` is empty (None), a non-explicit `template <class F> requires
std::is_invocable_r_v<Value, F&> RenderFn(F f)` wraps `f` once, `Value
operator()() const` calls it (empty: throws `rlmesh::ValueError`), `explicit
operator bool() const noexcept` tests for a target, `operator==` is true
for the same shared target or both empty, and `std::hash<RenderFn>` hashes
the shared target's address (0 when empty), so `std::hash<FrameSources>`
agrees with `==`. Rust `RenderFn` likewise implements `PartialEq`, `Eq` and
`Hash` by its id. A C++ `FrameSources` from
`Session::frame_sources()` or `RunContext::frame_sources()` borrows that
session or context for its `render` and must not outlive it, as in C. C
`_equals` compares `render` by source: both absent, the same
(`RLMeshRenderFn`, `user_data`) pair for caller-made sources, and for a
library-made source only the same handle. Python's repr prints a callable with
its address, which a native language cannot reproduce: native `repr` /
`Display` print a set `FrameSources.render` or `StepEvent.read` as
`<function>` (`None` when absent) and follow Python's text otherwise.

### Behaviour (every language)

- **Which loop.** A local `Model` runs `run` / `Model.run` on the native
  runtime loop. A `RemoteModel` and `RANDOM_SAMPLE` run on the session loop,
  as does every `Session` (a sandbox model will too, when sandbox parity
  lands with Remote's sandbox clients). `prefetch_lead != 0` on the
  session loop fails with ValueError before anything dials
  (`py/_models/base.py:1807`).
- **Episode budget.** `resolve_episode_budget` (`py/_models/_eval.py:178-195`)
  runs first everywhere: no `episodes` and no `seeds` is 1 episode; only
  `seeds` is `len(seeds)` (`[]` is 0); `episodes` with `seeds` of another
  length fails with ValueError. Zero episodes returns an empty `RunResult`;
  `Model.run` then never dials the env, still fires `on_run_start` and
  `on_run_end`, and its context keeps `contract` None
  (`py/_models/base.py:1213-1219`).
- **Trials.** Episode i walks `trial_index_base + i`, delivered as
  `reset(options={"trial_index": ...})` only to an env that declares the
  option, and recorded on `EpisodeResult.trial` whether or not the env
  declares it (RUN-P14); `trial` is None only under `NEXT_STEP` on the native
  loop, where the env restarts its own lanes
  (`crates/rlmesh-runtime/src/driver.rs:470-484`). `Session.reset(trial_index=)`
  on an env that does not declare it resets without it and warns
  (`UserWarning`, R-23).
- **Step bound.** A cap hit marks the episode `truncated`. Without
  `max_episode_steps`, the session loop and a native run whose driver owns
  resets (autoreset `DISABLED` or `UNSPECIFIED`, the edition's driver-owned
  modes) truncate at the edition default of 100,000
  steps (`py/_models/_eval.py:65`; `crates/rlmesh-runtime/src/driver.rs:1897-1900`,
  `crates/rlmesh-proto/src/lib.rs:256-260`). Under `NEXT_STEP` autoreset the env
  owns lane resets: no default bound applies, and explicit caps, seeds and a
  non-zero `trial_index_base` are refused at connect with ValueError
  (`crates/rlmesh-runtime/src/spec.rs:256-281`).
- **Validation order (RUN-5).** Checks that need only the options run before
  anything dials, with ValueError: `episodes` / `seeds` agreement,
  `execution_horizon` in 1..=1024 and, for a local `Model`, at most its
  `native_chunk`; `max_episode_steps >= 1`; `max_episode_seconds > 0` and not
  NaN (`+inf` = no cap); `prefetch_lead` 0 on the session loop; the `View`.
  Checks that need the peer run when it answers: a `RemoteModel`'s
  `native_chunk` at route resolution (ModelException with the server's code,
  `crates/rlmesh/src/model/engine.rs:1272-1299`), a vector env on the session
  loop (`num_envs > 1`, ValueError at connect, `py/_models/_resolve.py:74-86`),
  the autoreset refusals above, and on the native loop the two vector-env
  refusals below (ValueError at connect, RUN-P1).
- **Vector envs (native loop).** The budget bounds episode starts; lanes
  rolled past it go unscored. Driver-owned resets on a vector env need a lane
  endpoint (`subset_step`), which is driven as one single-lane group per lane;
  without one, `num_envs > 1` under a driver-owned mode is refused at connect
  with ValueError (`crates/rlmesh-runtime/src/spec.rs:319-329`, RUN-P1).
  A lockstep vector env (`num_envs > 1`, no `subset_step`) with
  `execution_horizon > 1` is refused at connect with ValueError under any
  autoreset mode (the same class as the refusal above, so their order is not
  observable), because chunk replay is whole-batch and one lane's episode end
  discards every lane's buffered frames (`crates/rlmesh/src/model/local.rs:74-81`,
  RUN-P1). Seeds are consumed one per episode start, indexed by episode slot
  (`crates/rlmesh-runtime/src/driver.rs:559-565,595-605`), so any `seeds`
  list that matches the budget is covered; no multiple of `num_envs` is
  required (RUN-P10). On the session loop a connected `num_envs` is always 1.
- **Hook order.** `on_run_start(context)`, then per episode
  `on_episode_start(episode, seed)`, `on_step(event)` zero or more times,
  `on_episode_end(result)`, then `on_run_end(result)`; vector episodes
  interleave. Hooks run serially and the env is idle while one runs (RUN-8).
  A hook error aborts the run. `on_run_end` fires exactly once, also on an
  error or a token cancel, with the completed episodes (a dropped Rust
  `_async` future fires no hook, R-18). The first error wins on both loops:
  the run's own error over one raised by `on_run_end`, which is swallowed, as
  Python's native loop does today (`py/_models/base.py:1234-1241`); on the
  session loop that error also wins over `on_run_end`'s and the model's
  `on_episode_end` for the last episode, and `on_run_end`'s over that
  `on_episode_end`'s (RUN-P11). On success an `on_run_end` error fails the
  run.
- **Index.** `EpisodeResult.index` and `StepEvent.episode` are 0-based; the
  runtime's 1-based ordinal is converted (`py/_models/base.py:1250-1253`).
- **RunContext before connect (RUN-6).** On the native loop `on_run_start`
  fires before the env is dialed: `contract` is None, `num_envs` is 1,
  `frame_sources()` returns no roles and no render source in every language
  (Python binds the context's env only after its loopback server starts,
  `py/_models/base.py:1210-1213,1364-1367`), and `read` fails with
  AdapterResolutionError (`py/_models/_eval.py:1580-1617`,
  `py/_models/_read.py:179-182`). Render becomes reachable only after
  connect, under RUN-7. A session connects before `on_run_start`.
- **Borrowing (R-17, X-7).** A run never closes the model. It releases what it
  made (the env relay for a local env (RUN-25), a factory-built env, its
  internal session, a connection it dialed). `close_env` shuts the caller's
  env: the wire close op for an address, `shutdown` for a handle, `close()`
  for a local env (`py/_models/base.py:1398-1414`). A remote handle that holds
  the env's single session slot makes a run fail with RuntimeError
  (`py/_models/base.py:1389-1397`). In C, a run or session over an
  `RLMeshEnv*` / `RLMeshVectorEnv*` that is already being served or driven
  fails with `RLMESH_ERR_RUNTIME`, and the handle is marked driven until the
  run returns or the session is freed, so a server cannot take it meanwhile
  (ENV-28; Env's C handle rules). C++ `Env&` / `VectorEnv&` targets pass the
  same handle and fail with `rlmesh::RuntimeError`. C# targets pass the same
  handle (an authored `IEnv` is wrapped in a C env handle for the call or
  session) and fail with `RLMesh.RuntimeError`; the session or run also holds
  a `DangerousAddRef` on every handle it borrows (R-17 C#).
- **Served-model targets.** `RemoteModel.session` refuses a set
  `instruction` or `trust_entrypoints` with ValueError
  (`py/_client/_remote_model.py:109-118`), then takes its env as follows: an
  address is dialed at creation and owned by the session; an `EnvServer`
  (Rust `&EnvServer`, C `rlmesh_env_server_target`, C++ `const EnvServer&`)
  is accepted, the model is bound with the server's `env_contract` and no env
  offer, and the session dials the server's address at its first env use and
  owns and closes that connection; a remote handle is used as is; a local
  env, vector env or factory is TypeError (`py/_client/_remote_model.py:126-158`;
  details in [Remote](remote.md)). It dials the model at creation
  (ConnectionError on failure). `RANDOM_SAMPLE` accepts both keywords.
- **Workflow edition.** Resolved by Core's chain; the model-class tier
  applies only to a local `Model` (`py/_client/_remote_model.py:122-125`).
  `selected_workflow_edition` on a session over a local env object fails with
  RuntimeError (`py/_models/_eval.py:951-957`).
- **Viewer.** The skip key truncates the current episode; quit truncates it
  and `Session.run` returns the partial result successfully
  (`py/_models/_eval.py:1214-1224,1466-1467`).
- **Session lifetime.** `Session.run` leaves the session open. `close()` is
  Python's normal `__exit__`: it holds the viewer unless the last `run`
  failed, fires the model's `on_episode_end` for an open episode (not the
  run hook), releases the model client, owned source and env, and returns
  the first release error (`py/_models/_eval.py:1483-1533`). Its contexts'
  `contract`, `num_envs`, `read` and `frame_sources()` then fail with
  RuntimeError too (RUN-7). `Session.run`
  also fires the model's `on_episode_end` for its last episode before
  returning, on success or error (`py/_models/_eval.py:1469-1477`; its error
  never replaces an earlier one, RUN-P11). `close()` is idempotent;
  afterwards every method fails with RuntimeError except `done` and
  `cancel_handle`.
  Drop, the C++ destructor and `rlmesh_session_free` act as `__exit__` on an
  exception: no hold, errors swallowed, bounded as R-17's "Session Drop"
  states. Rust Drop inside an async execution context (R-16's condition, a
  `spawn_blocking` closure included) follows that rule: the model's
  `on_episode_end` is queued through the `Model` (MDL-7) and a borrowed env
  is not closed even with `close_env`. A cancelled run ends its open episode
  as on any other error (R-18). `rlmesh.run` over a session closes it the
  same two ways (`py/_models/base.py:1813-1836`).
  C# (R-17): `Close()` is `close()`; `Dispose()` is `rlmesh_session_free`
  (the `__exit__`-on-exception path, always outside a runtime, so the model's
  `on_episode_end` runs and `close_env` closes a borrowed env on the
  disposing thread); a session reached only by the finalizer is freed on
  R-28's cleanup thread. The session holds `DangerousAddRef` on the model,
  env and remote handles it borrows until it is disposed or finalized, so a
  model or env disposed first stays alive natively (its own C# calls then
  throw `ObjectDisposedException`, D-41) while `Close()` on them is
  Python's close and fails the session's next call as Python does. After
  `Dispose()` every member, `Done` and `CancelHandle()` included, throws
  `ObjectDisposedException`; after `Close()` they behave as above.
- **Misuse.** `reader()` with no items is TypeError
  (`py/_models/_eval.py:1272-1275`).
- **One run per model (RUN-9).** A second `run` on a `Model` while one is in
  progress, from any thread, fails at once with RuntimeError. Predicts from
  runs and sessions serialize on the model; another session on the same model
  may predict from a hook mid-run. A hook cannot drive its own running
  session (RUN-28).
- **Hook dispatch (RUN-8).** The sync entry points (`rlmesh::run`,
  `Model::run`, `Session::run`, every C and C++ run, and Python's `Model.run`
  through the facade, RUN-P12) call hooks outside
  any async execution context: the calling thread polls the driver in R-17's
  segments (the library's parking executor inside `Handle::enter`, never
  tokio's `block_on`) until the next relay event, runs the hook on its own
  stack with the driving flag clear, acknowledges, and resumes polling. Sync rlmesh calls from a hook are
  therefore allowed (R-16), including a session context's `render()` of a
  remote env (RUN-7). Hooks of a Rust `*_async` twin run inside the caller's
  executor and must not make blocking rlmesh calls: they fail with
  `Error::Runtime` (R-16), a session context's remote `render()` included; a
  local env's `render()` is a direct call and works. A sync rlmesh call from
  a `spawn_blocking` closure a hook starts is refused the same way (R-16).
  C#: the sync entry points run hooks on the calling thread, as C; a twin
  (`RunAsync`) runs the sync C call on its own thread (R-16 C#), so its
  hooks and relayed env ops run there, outside any async context, and may
  make sync rlmesh calls, a session context's remote `render()` included.
  So a `Recorder` capture under a C# twin over a remote env records
  `render()` frames, unlike under a Rust twin. RUN-30 holds with "the
  dispatching thread" being the twin's thread. Neither path marshals to a
  `SynchronizationContext`: a hook that touches engine objects (Unity) under
  `RunAsync` dispatches to the main thread itself (R-28).
- **Threading (C, C++, C#).** Hooks run serially on the thread that called
  `rlmesh_run`, `rlmesh_model_run` or `rlmesh_session_run`. Inside its own
  hooks the running session allows only what a Rust hook can reach (RUN-28):
  the `RunContext` members `contract`, `num_envs`, `read` and `frame_sources`
  (C `rlmesh_session_*` of those names), `run_context` and `cancel_handle`
  (whose results a Rust hook holds as the context it received and a token
  cloned before the run), plus every `rlmesh_run_context_*`,
  `rlmesh_step_event_*` and value call. `reset`, `step`, `predict`, `run`,
  `close`, `reader`, `observation_roles`, `selected_workflow_edition` and
  `done` on it fail with RuntimeError (RUN-28, RUN-P7), as does `run` on the
  running model (RUN-9); `rlmesh_session_free` on it
  from its own hook is a caller error, unchecked, as Env's rule against
  `_free` from a callback. Other handles, another session on the
  same model included, may be used. Those own-hook refusals are a separate
  case from overlap, below.
  Handles may move between threads. An `RLMeshSession` (C++ `Session`)
  call that overlaps another call on the same session from another thread,
  or re-enters it outside RUN-28's own-hook case, fails with
  `RLMESH_ERR_RUNTIME` / `rlmesh::RuntimeError` (R-18's refusal of
  overlapping calls, R-21's misuse row), never UB; the exceptions are
  `rlmesh_session_cancel_handle` and `rlmesh_session_done`, which read state
  kept outside the per-call guard and may overlap any call from any thread
  (`done` still fails inside the session's own hooks, RUN-28), as Remote's
  accessors and `cancel_handle` do. A run's calls on its own session from
  its hooks, on the dispatching thread, are RUN-28's, not overlap. A
  canceller thread therefore calls `rlmesh_session_cancel_handle` once and
  `rlmesh_ext_cancel_token_cancel` on the result at any time. `RLMeshReader`
  (`rlmesh_reader_call`) and `RLMeshRunHooks` (each `rlmesh_run_hooks_on_*`,
  and a run's dispatch to it) refuse an overlapping or re-entrant call on
  the same handle the same way; `rlmesh_reader_roles_len` / `_get` read
  immutable state and may overlap any call. `RLMeshRecorder` serializes its
  calls on the internal lock that also guards the state its capture handles
  share (RUN-14), so its calls and its captures' hooks may run on any
  threads at once. `RLMeshRunResult`, `RLMeshRunContext` and the record and
  telemetry handles are immutable or internally synchronized and shareable.
  Model callbacks follow [Model](model.md). C# keeps every rule above: its
  wrapper adds no lock of its own, so an overlapping `Session` call reaches
  C and fails with `RLMesh.RuntimeError`; `Done` and `CancelHandle()` may
  overlap any call. The twins count as calls on their own thread: two
  concurrent `StepAsync` on one session overlap and the second fails.
